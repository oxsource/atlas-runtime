# Feature 管理总则

本文档定义 Atlas 项目中新特性（feature）与提议（proposal）的收集、评审、流转与实现流程，确保所有功能演进有迹可循、决策透明。

---

## 一、总则

### 1.1 适用范围

本规范适用于 Atlas 项目中**所有功能演进**的提议管理，包括但不限于：

- 新模块 / 新后端接入
- 现有模块能力增强（如 Pipeline 扩展、API 新增方法）
- 跨阶段的大型特性
- 架构调整 / 重构
- 三方依赖升级或替换

> 缺陷修复不属于 Feature 范畴，请遵循 `docs/bugfix_spec.md`。

### 1.2 核心原则

| 原则 | 说明 |
|------|------|
| **先提议，后实现** | 任何非平凡改动须先有文档化的提议，经讨论达成共识后再编码 |
| **单一职责** | 每份提议只聚焦一个主题，避免合并多个不相关特性 |
| **可追溯** | 提议的状态流转、评审结论、驳回理由均须留档 |
| **渐进细化** | 提议池（草案）→ 阶段方案（详细设计）→ 代码实现，逐层细化 |

## 二、Feature 分类与流转路径

根据特性规模，分为三类，对应不同的管理流程：

```
┌─────────────────────────────────────────────────────────┐
│                    Feature 来源                          │
└──────────────┬──────────────────┬───────────────────────┘
               │                  │
               ▼                  ▼
    ┌──────────────────┐  ┌───────────────────┐
    │ 零散提议 / 想法   │  │ 模块级改进 / TODO  │
    └────────┬─────────┘  └─────────┬─────────┘
             │                      │
             ▼                      │
    ┌──────────────────┐            │
    │ proposals/ 草案   │◄───────────┘
    │ (Proposal-NNN)   │
    └────────┬─────────┘
             │ 评审讨论
             ▼
    ┌──────────────────┐
    │  已采纳           │
    └────────┬─────────┘
             │ 转为详细设计
             ▼
    ┌──────────────────┐
    │ docs/phase{N}.md │  补充 Feature/Bugfix 记录引用
    │ (记录章节)        │
    └────────┬─────────┘
             │ 按 phase_spec.md 流程实现
             ▼
    ┌──────────────────┐
    │  代码合并 + 归档   │
    └──────────────────┘
```

### 2.1 三类特性对照

| 类型 | 规模 | 示例 | 管理方式 |
|------|------|------|----------|
| **阶段级大特性** | 跨多模块、需独立排期 | 多后端动态加载、C API 绑定、Python SDK | `proposals/` 草案 → 采纳后补充到最相关的已有 `phase{N}.md`，按 `phase_spec.md` 流程实现 |
| **模块级改进** | 单模块增强、已有 TODO 的沉淀 | Pipeline 自定义节点、新增预处理节点、日志库接入 | 记入 `proposals/`，采纳后补充到对应阶段的 `phase{N}.md` |
| **小型特性** | 改动范围小、争议低 | 新增 `ErrorCode` 枚举值、补充工具脚本 | 可直接在 `proposals/` 中简述方案，采纳后直接实现，无需关联 phase 文档 |

> **重要约束**：项目阶段划分为固定框架（阶段一至六），**不再新增阶段**。所有 feature 提议经评审采纳后，只能关联补充到已有的阶段文档中，不得创建新的 `phase{N}.md`。

## 三、Proposals 目录规范

### 3.1 目录结构

```
docs/
├── proposals/                        # 提议收集池
│   ├── README.md                     # 本文档的子集：目录说明与模板
│   ├── 001-pipeline-custom-nodes.md  # 编号 + 短标题
│   ├── 002-model-encryption.md
│   └── ...
├── architecture.md
├── phase_spec.md
├── phase1.md
└── ...
```

### 3.2 命名规则

```
NNN-short-kebab-title.md
```

- `NNN`：三位递增编号，从 `001` 开始，不回收、不重排
- `short-kebab-title`：英文小写短标题，连字符分隔，如 `pipeline-custom-nodes`

### 3.3 提议文档模板

每份提议须包含以下结构：

```markdown
# Proposal-NNN: <标题>

> **提议日期**：YYYY-MM-DD
> **提议人**：<姓名 / GitHub ID>
> **状态**：草案 / 讨论中 / 已采纳 / 已驳回
> **类型**：阶段级 / 模块级 / 小型
> **关联**：<引用相关的 phase 文档、architecture 章节、issue 编号等，无则填「无」>

## 一、背景

<为什么需要这个改动？当前存在什么问题或不足？>

## 二、方案概要

<1-3 段描述核心思路，无需完整设计细节。可附简图。>

## 三、影响范围

<涉及的模块、是否影响公共 API / ABI、是否引入新依赖、预估工作量。>

## 四、后续动作

- [ ] 评审讨论（记录日期与结论）
- [ ] 若采纳：补充到已有 `phase{N}.md` 或直接实现
- [ ] 若驳回：填写驳回理由
```

## 四、状态流转

### 4.1 状态定义

| 状态 | 含义 | 触发条件 |
|------|------|----------|
| `草案` | 初稿，待提交讨论 | 提议人创建文档 |
| `讨论中` | 已提交，等待或正在进行评审 | 提议人将状态改为「讨论中」并通知相关开发者 |
| `已采纳` | 评审通过，同意实施 | 讨论达成共识 |
| `已驳回` | 评审未通过或不再需要 | 讨论后决定不实施；文档保留，不删除 |

### 4.2 流转规则

```
草案 ──(提交评审)──► 讨论中 ──(达成共识)──► 已采纳
                        │
                        └──(否决/搁置)──► 已驳回
```

- `已采纳` 的提议须在「后续动作」中注明：补充到哪个已有 `phase{N}.md`（阶段级 / 模块级）或直接实现（小型）；
- `已驳回` 的提议须在文档末尾补充「驳回理由」小节，保留供后续回溯；
- 状态变更时同步更新 `提议日期` 下方的状态字段。

### 4.3 采纳后的去向

| 类型 | 采纳后动作 |
|------|-----------|
| 阶段级 | 补充到最相关的已有 `phase{N}.md`（按 4.5 节规范标注），在提议文档「后续动作」中标注 `→ phase{N}.md (补充)`，按 `phase_spec.md` 流程实现 |
| 模块级 | 补充到对应阶段的 `phase{N}.md`，在提议文档中标注去向 |
| 小型 | 直接编码实现 + PR，提议文档标注对应 PR 编号后归档 |

> **禁止新建阶段**：无论 feature 规模大小，采纳后只能补充到已有阶段文档，不得创建新的 `phase{N}.md`。

### 4.4 阶段归属确认

提议被采纳后，须在「后续动作」中**明确声明该 feature 补充到哪个已有阶段文档**。所有 feature 只能补充到已有阶段，不得新建阶段：

| 情况 | 处理方式 | 示例 |
|------|----------|------|
| **补充单一阶段** | 在已有 `phase{N}.md` 中追加内容，须按 4.5 节规范标注；提议文档标注 `→ phase{N}.md (补充)` | Pipeline 自定义节点 → 补充 `phase2.md` |
| **补充多个阶段** | 涉及多个已有阶段文档时逐一列出，均标注为「补充」 | API 重构 → `phase3.md (补充)` + `phase2.md (补充)` |

> **禁止新建阶段**：`phase{N}.md` 的数量固定为阶段一至六，后续所有 feature 只能以补充形式追加内容。

提议文档「后续动作」中须补充如下声明：

```markdown
## 四、后续动作

- [x] 评审讨论（2026-06-26，通过）
- [x] 阶段归属：
  - `→ phase2.md`（补充：第七章「Manifest 自由配置 Pipeline」详细设计方案）
- [ ] 实现完成后更新本文档状态为「已采纳」并归档
```

> **注意**：上述示例中的阶段归属只能为「补充已有阶段」，不得出现「新建阶段」。

### 4.5 已有阶段文档的补充标注规范

当采纳的 feature 需要在**已定稿的 `phase{N}.md`**（状态为「已实现」）中追加内容时，所有新增/修改的内容块须附带**补充标注**，明示该内容并非原始阶段设计的一部分，而是后续 feature 追加的。

> **补充内容原则**：阶段文档的补充章节**仅保留对提议的引用**（背景说明 + 提议文档路径），详细方案由提议文档自身承载，不重复其内容。详见 `phase_spec.md` Step 1 「补充章节规范」。

**Feature / Bugfix 记录章节：**

每个 `phase{N}.md` 须包含「Feature 记录」与「Bugfix 记录」两个固定章节（详见 `phase_spec.md` Step 1）。记录表格中的 Proposal / BUG 列以 **Markdown 链接**直接指向对应文档路径，不再单独列出关联说明行：

```markdown
## Feature 记录

| Proposal | 日期 | 简述 | 状态 |
|----------|------|------|------|
| [Proposal-001](proposals/001-pipeline-manifest-config.md) | 2026-06-26 | Manifest 自由配置 Pipeline | 已采纳 |

## Bugfix 记录

| BUG | 日期 | 简述 | 等级 | 状态 |
|-----|------|------|------|------|
| [BUG-003](bugfixes/BUG-003-empty-models-crash.md) | 2026-06-26 | 空模型数组导致崩溃 | P0 | 已修复 |
```

> 新增记录时直接在表格末尾追加一行，Proposal / BUG 列填入 `[编号](相对路径)` 格式的链接即可。

**标注格式：**

在补充内容块的**开头**添加引用块：

```markdown
> **【补充】** Proposal-001 | 2026-06-26 | 文档版本 1.0.0 → 1.0.1
> 以下内容由 Proposal-001 评审采纳后追加，非阶段原始设计。

（补充的具体内容...）
```

**字段说明：**

| 字段 | 说明 |
|------|------|
| `Proposal-NNN` | 触发本次补充的提议编号 |
| 日期 | 补充内容写入的日期 |
| 文档版本 | 标注版本变化，如 `1.0.0 → 1.0.1`（补丁级递增） |

**版本递增规则：**

| 补充类型 | 版本递增 | 示例 |
|----------|----------|------|
| 笔误修正、格式调整 | 不递增 | — |
| 追加说明性内容（TODO、备注、局限性记录） | 补丁级（patch +1） | `1.0.0 → 1.0.1` |
| 修改设计方案（接口签名、数据结构变更） | 次版本级（minor +1） | `1.0.0 → 1.1.0` |

> 修改已实现阶段的设计方案属于重大变更，须确保与现有代码的一致性，必要时同步更新 `phase{N}_result.md`。

**示例（`phase2.md` 中补充 TODO）：**

```markdown
> **【补充】** Proposal-001 | 2026-06-26 | 文档版本 1.0.0 → 1.0.1
> 以下局限性由 Proposal-001 评审采纳后追加记录。

**已知局限性（TODO，后续阶段优化）：**

1. 节点顺序固定，用户无法在清单中调整...
2. 仅支持 inputs[0]...
```

补充后，`phase{N}.md` 顶部版本头中的「文档版本」字段须同步更新：

```markdown
> **文档版本**：1.0.1    ← 原 1.0.0
> **对应代码版本**：v1.0.0
> **最后更新**：2026-06-26    ← 更新为补充日期
> **状态**：已实现
```

## 五、与现有文档体系的关系

```
architecture.md（总则：架构与阶段划分）
        │
        │  提议评审依据
        ▼
proposals/（提议池：草案收集与评审）──采纳──► docs/phase{N}.md（阶段方案）
                                              │
                                              │  按 phase_spec.md 流程
                                              ▼
                                         代码实现 + 测试
                                              │
                                              ▼
                                     CHANGELOG.md（版本记录）
                                     phase{N}_result.md（阶段归档）
```

| 文档 | 职责 | 更新时机 |
|------|------|----------|
| `proposals/NNN-*.md` | 收集想法、记录评审结论 | 提议创建时、状态变更时 |
| `architecture.md` | 总体架构与阶段划分（固定为阶段一至六，不再新增） | 阶段内容重大调整时更新 |
| `phase_spec.md` | 阶段开发流程规范（含本总则的引用） | 流程调整时 |
| `phase{N}.md` | 单个阶段的详细设计方案 | 阶段启动时创建，评审后定稿 |
| `phase{N}_result.md` | 阶段交付归档 | 阶段完成时 |
| `CHANGELOG.md` | 面向用户的版本变更记录 | 代码合并 / 版本发布时 |

## 六、与 phase_spec.md 的衔接

在 `phase_spec.md` 的标准流程中，于 Step 1 之前增加 **Step 0 — 提议收集与补充**：

```
proposals/（提议池）
       │
       │  评审采纳
       ▼
[Step 0] 确定补充到哪个已有 phase{N}.md
       │
       ▼
[Step 1] 在已有 phase{N}.md 中形成补充设计文档
       │
       ▼
[Step 2] 开发者评估文档，确认方案
       │
       ▼
[Step 3] 实现代码 + 单元测试
       │
       ▼
[Step 4] 构建验证，所有测试通过
       │
       ▼
[Step 5] 编写阶段结果文档（phase{N}_result.md）
       │
       ▼
[Step 6] git commit
```

**Step 0 说明：**

- 目的：在正式编写阶段方案前，先通过提议池完成想法收集与初步评审；
- 产出：`proposals/NNN-*.md` 文档，状态流转至「已采纳」；
- 补充条件：提议被采纳后，确定补充到最相关的已有 `phase{N}.md`（不创建新阶段）；
- 小型特性经提议采纳后可直接进入 Step 3 实现，跳过 Step 1/2。

## 七、实践要点

### 7.1 何时应该创建提议

- 任何需要超过 1 小时思考的设计决策；
- 涉及公共 API 变更（新增、修改、删除接口）；
- 引入新的三方依赖；
- 改变现有模块的职责边界；
- 对已有行为的语义性修改（非纯 bugfix）。

### 7.2 何时可以跳过提议

- 紧急 bugfix（先修后记，在 CHANGELOG 中说明）；
- 纯文档订正（错别字、格式修正）；
- 测试用例补充（不改变生产行为）；
- 重命名局部变量等不影响接口的代码清理。

### 7.3 提议编号管理

- 编号严格递增，即使提议被驳回，编号也不回收；
- 编号不补零对齐位数（始终三位 `001`-`999`），超过 999 后扩展为四位；
- 不允许重命名已创建的提议文件（编号即身份标识）。

### 7.4 评审节奏

- 无固定评审会议，采用异步讨论（PR 评论 / Issue / 文档批注）；
- 提议提交后，相关开发者应在 **5 个工作日**内给出反馈；
- 超过 5 个工作日无异议且无修改请求，提议人可将状态推进至「已采纳」；
- 有争议的提议不适用默认通过，须显式达成共识。

## 八、快速上手 Checklist

新特性从想法到落地的完整步骤：

- [ ] 1. 在 `docs/proposals/` 创建 `NNN-short-title.md`，按模板填写
- [ ] 2. 状态设为「草案」，通知相关开发者
- [ ] 3. 状态推进至「讨论中」，收集反馈
- [ ] 4. 达成共识后，状态改为「已采纳」
- [ ] 5a. 阶段级 / 模块级：补充到已有 `docs/phase{N}.md`，走 `phase_spec.md` 流程
- [ ] 5b. 小型：直接编码 + PR，提议文档标注 PR 编号
- [ ] 6. 实现完成后，更新 `CHANGELOG.md`
- [ ] 7. 提议文档状态最终确认，归档留存
