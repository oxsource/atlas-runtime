# 文档管理总则

本文档定义 Atlas 项目中文档的编写、维护与定期梳理规范，确保文档体系的一致性与可追溯性。

---

## 一、文档体系

```
docs/
├── architecture.md          # 总则：整体架构、模块说明、阶段划分
├── code_spec.md             # 代码规范（全局适用）
├── doc_spec.md              # 本文档：文档管理规范
├── feature_spec.md          # Feature 管理总则
├── bugfix_spec.md           # Bugfix 管理总则
├── phase_spec.md            # 阶段开发规范与流程
├── proposals/               # 提议收集池
│   ├── README.md
│   └── NNN-*.md
├── bugfixes/                # 缺陷报告池（按需创建）
│   └── BUG-NNN-*.md
├── phase1.md ~ phase6.md    # 各阶段设计方案（固定，不再新增）
└── phase{N}_result.md       # 各阶段结果汇总（按需创建）
```

### 文档分类

| 类型 | 文件 | 版本头 | 说明 |
|------|------|--------|------|
| 总则 | `architecture.md` | 不需要 | 架构总纲，阶段划分固定为阶段一至六 |
| 规范 | `code_spec.md`、`doc_spec.md`、`feature_spec.md`、`bugfix_spec.md`、`phase_spec.md` | 不需要 | 全局适用的流程与规则 |
| 阶段方案 | `phase{N}.md` | **必须** | 每个阶段的设计文档，固定 6 份 |
| 阶段结果 | `phase{N}_result.md` | 不需要 | 阶段完成后的交付归档，按需创建 |
| 提议 | `proposals/NNN-*.md` | 使用 Proposal 模板头 | Feature 提议，编号递增不回收 |
| 缺陷报告 | `bugfixes/BUG-NNN-*.md` | 使用 Bug Report 模板头 | 缺陷记录，编号递增不回收 |

## 二、编写规范

### 2.1 版本头

仅 `phase{N}.md` 须包含版本头（格式见 `phase_spec.md`）。规范文档与总则文档不需要版本头。

### 2.2 章节编号

- 每篇文档的章节编号须**唯一且连续**，禁止出现重复章节号；
- 使用中文数字（一、二、三...）或阿拉伯数字（1、2、3...），全文统一风格。

### 2.3 内部链接

- 引用项目内文档时使用 **Markdown 相对链接**，路径相对于 `docs/` 目录；
- 示例：`[Proposal-001](proposals/001-pipeline-manifest-config.md)`；
- 引用不存在的文件（如示例演示）时，须在上下文中标注「示例」字样。

### 2.4 术语一致性

| 术语 | 正确用法 | 禁止用法 |
|------|----------|----------|
| Pipeline 节点配置字段 | `name` | ~~`type`~~ |
| 阶段编号 | 阶段一至阶段六（固定） | ~~阶段七及以后~~ |
| Feature 归属动作 | 补充到已有阶段 | ~~新建阶段 / 立为新阶段~~ |
| 示例程序 | `examples/two_model_pipeline` | ~~`examples/external_consumer`~~（已删除） |

### 2.5 补充内容原则

- 阶段文档的补充章节**仅保留对提议的引用**（背景 + 提议路径）；
- 详细方案由提议文档自身承载，不重复其内容；
- Feature / Bugfix 记录以 Markdown 链接形式填入表格，不单独列出说明行。

## 三、定期梳理机制

### 3.1 触发条件

当满足以下任一条件时，须进行一次全量文档梳理：

| 条件 | 说明 |
|------|------|
| 文档变更累计达到 **10 次提交** | 通过 `git log --oneline docs/` 统计 |
| 新增 / 采纳 **3 个以上 Feature 提议** | 提议池中状态为「已采纳」的数量 |
| 发生 **架构性变更** | 如模块职责调整、公共 API 变更 |
| 距上次梳理超过 **30 天** | 定期回溯 |

### 3.2 梳理检查清单

梳理时按以下清单逐项检查：

| 检查项 | 检查方法 | 通过标准 |
|--------|----------|----------|
| 版本头完整性 | 检查所有 `phase{N}.md` | 版本头存在且字段完整 |
| 章节编号唯一性 | 通读每篇文档 | 无重复章节号 |
| 内部链接有效性 | 检查所有 Markdown 链接 | 无断链（示例标注的除外） |
| 术语一致性 | 全文搜索禁止用法的术语 | 无违规 |
| 状态一致性 | 对比提议状态与阶段记录 | 提议「已采纳」的须在对应阶段 Feature 记录中存在 |
| 补充内容合规 | 检查阶段文档中的补充章节 | 仅含引用，无详细设计重复 |
| Feature/Bugfix 记录 | 检查所有 `phase{N}.md` | 均包含两个固定章节（可为空表） |
| 重复内容 | 通读阶段文档 | 无新旧版本并存（如 phase3.md 旧版残留） |
| 文档体系一览 | 对比 `phase_spec.md` 中的目录树 | 与实际文件一致 |

### 3.3 梳理记录

每次梳理完成后，在本文档末尾追加一条梳理记录：

```markdown
### YYYY-MM-DD 文档梳理

- 触发条件：<具体条件>
- 检查项数：<N>
- 发现问题：<N>
- 修复问题：<N>
- 遗留问题：<描述或「无」>
```

### 3.4 梳理职责

- 文档梳理由**开发者发起**，AI 辅助执行检查与修复；
- AI 发现问题后须向开发者报告，由开发者确认后再修改；
- 梳理结果作为一笔独立提交，commit message 格式：`docs: periodic doc review — <日期>`
